# P-002 镜像运维（多镜像管理、可用性检测、失败自动回退）

## 背景

- 定位：在 P-001 单镜像引擎之上补齐镜像可靠性——公共镜像稳定性参差是立论事实（ghproxy.net 实装 release 404 而浏览器快筛曾可用；ghfast.top 与 moeyy 不可用；gh-proxy.com 全链路可用）
- 机制（S1/S1b 实证，2026-09-03）：`request-url` 请求的响应经同名请求 ID 频道回达，载荷 `(sender, response)` 含 `status` 与完整 `headers`——发送时同步在 ID 频道挂自有监听，即可被动截获真实流量的成败信号，零额外流量
- 核心模型：**目录即偏好**——内置目录有序（最优在前）本身暗含偏好；插件全自动切换，设置页不提供镜像选择，只读显示当前使用的镜像（active）
- 定稿细化一处判定：`/releases/download/` 路径 404 实为镜像覆盖缺失信号（更新请求的版本号源自市场数据、上游应存在），与探索期初判相反；raw 路径 404 才是下架真值
- 约束：不考虑移动端；不发布社区插件库；仅实现前缀型镜像（`type` 判别字段预留其他替换方式）

## 用户故事

- 作为用户，当默认镜像故障时，我希望插件自动切换到下一可用镜像，无需我手动干预
- 作为用户，我希望在设置里看到插件当前实际使用的镜像
- 作为用户，我希望坏过的镜像在会话内不被反复尝试，重启或重载插件后重新获得机会
- 作为用户，我希望源站资源本就不存在（404 真值）时插件不误判为镜像故障

## 范围内

- 内置镜像目录：代码内有序常量（顺序即偏好与回退顺序），条目含 `type: 'prefix'` 判别字段与 `base`、`label`；目录随插件版本发布更新
- 被动健康观测：发送 `request-url` 时同步在请求 ID 频道挂一次性监听，按响应 `status` 对当前 active 镜像记账，响应到达或超时后移除监听
- 自动切换：失败即推进游标到目录下一项（跳过拉黑项）；同一项连续 3 败本会话拉黑；成功即稳定并清零该计数；全部拉黑后停留末位、失败如实呈现
- 拉黑冷却：拉黑带 30 分钟冷却期，期满自动解除并清零连败，重新进入轮转（每冷却周期每死镜像至多消耗约 1 个失败请求）
- 判定语义：超时、网络层错误回复、403/429、5xx、200 但内容异常计失败；`/releases/download/<版本>/` 路径 404 计失败（镜像覆盖缺失）；其余路径 404 计上游真值不计失败
- 设置页：`启用 GitHub 加速` 开关（默认开）+ 当前镜像控件化只读显示 + 镜像池有序只读展示（active/拉黑标记，1s 轮询实时跟随切换）+ `恢复初始状态` 按钮（清理拉黑与连败、游标回首项）；开关只承担加速启停职责，不承载状态复位（复位是独立动作）；`mirrorBase` 存储键废弃，旧 `data.json` 键忽略（零迁移）
- 生命周期：onload 重建游标与拉黑记录；unload 还原补丁（沿袭 P-001）

## 范围外

- 主动健康探测与频率策略（探索方向 B；被动观测成立后消解，留作演进）
- 目录运行时编辑、用户排序持久化、目录远程热更新
- 自建镜像与目录外自定义候选接入（留待「自定义候选前置」扩展，条目 `type` 结构已预留）
- 其他替换方式的实现（`host-map` 域名替换式等，仅预留 `type` 判别）
- 移动端支持、社区插件库发布
- 直连兜底（已否决，见 A-004）

## 验收标准

AC1：目录首项替换为必然失败的镜像（调试构建构造）时，市场列表请求自动切换至下一项且加载成功
AC2：同一镜像连续 3 次失败后被会话拉黑，本会话后续请求不再使用该镜像（探针核对请求前缀）
AC3：任一镜像成功服务请求后即稳定为 active，后续请求不回跳已拉黑项
AC4：`/releases/download/<版本>/` 的 404 不触发切换（版本真值路径不影响记账），5xx/超时/403 触发切换
AC5：设置页只读显示当前 active 镜像，自动切换发生后显示跟随变化
AC6：含旧 `mirrorBase` 键的 `data.json` 加载后不报错、不影响新逻辑
AC7：禁用再启用插件后游标与拉黑复位，曾拉黑镜像重新获得机会
AC8：非 GitHub 域请求行为与未启用插件时一致（P-001 AC7 回归）
AC9：加速开关关闭时全部请求直连（P-001 AC4 回归）
AC10：点击「重置镜像切换状态」后，游标回到目录首项、镜像池拉黑标记全部清除
AC11：拉黑满 30 分钟冷却期后自动解除并清零连败，重新进入轮转（单元级以注入时钟核对，E2E 可用缩短冷却常量的调试构建构造）

## 边界与异常

- 全部镜像拉黑：停留末位、错误如实呈现；恢复路径为重启或禁用再启用插件（onload 复位游标与拉黑）
- 响应记账三分类：含数字 `status` 按 HTTP 语义判定；含 `error` 字段（网络层失败——DNS 解析失败、连接拒绝、超时等，T-008 实测载荷为 `{"error":{}}` 形态）计镜像失败；其余无法判定的结构变化静默跳过记账，不抛错、不影响既有改写
- 监听泄漏防护：自有监听在响应到达或超时兜底后自摘，防止无响应请求累积监听
- 404 语义仅做 `/releases/download/` 与其余路径的二分，不做全量上游真值校验
- Obsidian 升级改变 `request-url` 通道或回复通道结构：改写与观测一并静默失效（沿袭 P-001 兜底风格）
