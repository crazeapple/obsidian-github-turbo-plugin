# P-001 GitHub 访问加速核心（镜像地址改写）

## 背景

- 产品形态：Obsidian 内置社区插件市场加速器——发现、安装、更新由内置流程承载，本插件专注加速层，不自带市场界面；不考虑移动端；不发布到社区插件库
- 机制（spike V1-V4 实证，2026-09-02）：Obsidian 桌面端内置市场的全部 GitHub 请求经 `ipcRenderer.send('request-url', <id>, { url, ... })` 过桥，URL 明文；renderer 侧改写该参数即可令主进程实际访问镜像地址
- 实测证据：无代理环境下列表加载明显变快；Templater 完整安装成功（release manifest、`main.js`、`styles.css` 均经改写链路）；默认镜像实测定向 `https://gh-proxy.com/`（ghproxy.net 实装 404，公共镜像稳定性参差）
- 技术基座：Obsidian 官方示例插件模板（TypeScript + esbuild）

## 用户故事

- 作为直连 GitHub 缓慢环境下的 Obsidian 用户，我打开社区插件与主题市场时列表快速加载
- 作为用户，我安装与更新插件时下载流量走镜像地址
- 作为用户，我可以一键关闭加速，立即恢复直连行为
- 作为用户，我可以在设置中更换镜像源地址

## 范围内

- 拦截 `ipcRenderer.send('request-url', ...)`，对参数中对象形态的 `url` 字段做前缀匹配改写，仅命中 `https://github.com/` 与 `https://raw.githubusercontent.com/`
- 镜像源地址可在设置页配置，默认 `https://gh-proxy.com/`
- 设置页总开关，默认开启
- 生命周期：插件 onload 时挂载 patch、unload 时还原、防重复挂载
- 改写幂等：已带镜像前缀的 URL 不二次改写

## 范围外

- 多镜像管理、可用性检测、失败自动回退——属 `I-001` M2 后续提案
- 自带市场、浏览、安装、更新界面
- 移动端支持
- 提交社区插件库审核（本地使用）
- 非 `github.com` / `raw.githubusercontent.com` 域名的任何请求改写
- 除默认镜像外其他公共镜像的可用性保证（用户可自行配置，不逐一背书）

## 验收标准

AC1：无系统代理环境下，开启加速，社区插件与社区主题的浏览列表均能完整加载
AC2：无系统代理环境下，开启加速，安装任一社区插件成功，其目录含完整 `manifest.json` 与 `main.js`（如插件含 `styles.css` 亦完整）
AC3：开启加速，「检查更新」正常返回并完成一次真实更新
AC4：关闭总开关并重载 Obsidian 后，GitHub 请求恢复直连（请求 URL 不再带镜像前缀）
AC5：设置中修改镜像源地址并重载后，改写使用新地址
AC6：禁用再启用插件（或重载 Obsidian）后，同一请求的 URL 不会被叠加两次镜像前缀
AC7：非 GitHub 域名请求（如账号登录、Obsidian Sync）行为与未启用本插件时一致

## 边界与异常

- 镜像请求失败：本版不做自动回退——错误原样呈现，用户手动更换镜像或关闭开关；自动回退属 M2
- 应用升级风险：Obsidian 升级可能改变 `request-url` 通道结构；patch 挂载前先探测校验频道名与参数结构，不匹配则不挂载、静默跳过（不抛错、不破坏原生市场功能），由总开关与卸载兜底
- 重定向：`github.com` release 下载的重定向链由镜像服务处理，实测 `gh-proxy.com` 满足
- 改写只做字符串前缀判断，不解析 GitHub API 语义、不缓存、不重试

## 依赖与关联

- 依赖 Obsidian 桌面端 IPC `request-url` 通道（spike V1-V4 于 2026-09-02 用户环境实证通过）
- 关联 `I-001`（M1 加速核心）；后续 M2 镜像运维提案复用本插件的镜像配置结构
- 关联修正案 A-001、A-002（被否备选留痕）
